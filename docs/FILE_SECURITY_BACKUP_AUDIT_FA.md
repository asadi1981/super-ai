# ممیزی امنیت فایل و پشتیبان‌گیری SUPER AI

تاریخ: 2026-11-06
شاخه: `design/core-architecture-v1`

## تغییرات اعمال‌شده
- مسیرهای فایل با resolve و commonpath به ریشه مجاز محدود می‌شوند.
- خروج از workspace یا backup root از طریق مسیر نسبی و symlink رد می‌شود.
- نوشتن فایل متنی با فایل موقت در همان پوشه و جایگزینی اتمی انجام می‌شود.
- snapshot و restore نیز از کپی موقت و جایگزینی اتمی استفاده می‌کنند.
- قبل از restore، SHA-256 فایل snapshot بررسی می‌شود.
- پیش از جایگزینی مقصد موجود، یک نسخه بازگشت (rollback snapshot) با نام یکتا در `restore-rollback/` ذخیره و SHA-256 آن ثبت می‌شود؛ مشخصات آخرین نسخه بازگشت در `BackupManager.last_rollback` در دسترس است.
- مسیر کپی اتمی اصلاح شد تا فایل موقت با دسترسی نوشتن باز بماند و `fsync` روی descriptor قابل نوشتن اجرا شود؛ این اصلاح برای رفع خطای مشاهده‌شده در Windows CI انجام شد.
- restore هم مسیر مطلق داخل backup root و هم مسیر نسبی به backup root را می‌پذیرد.
- snapshot و مقصد restore نمی‌توانند یک مسیر باشند.

## آزمون‌های افزوده‌شده
- جلوگیری از path traversal با `..`
- جلوگیری از symlink escape در workspace
- جلوگیری از symlink escape در backup root
- رد snapshot خارج از backup root
- پذیرش مسیر نسبی snapshot
- رد snapshot دستکاری‌شده بدون تغییر فایل مقصد
- snapshot و restore عادی
- خواندن/نوشتن متن فارسی و کنترل سیاست ابزارها

## نتیجه آزمون در محیط توسعه
۱۰ آزمون در محیط لینوکسی در دسترس اجرا شد و همگی PASS شدند. اجرای محلی با نسخه‌های فایل همسان‌سازی‌شده از محتوای شاخه توسعه انجام شده است؛ این نتیجه جایگزین اجرای رسمی GitHub Actions یا آزمون روی Windows 7 واقعی نیست.

## محدودیت‌های باقی‌مانده
1. بررسی مسیر و symlink در برابر حمله هم‌زمان (TOCTOU) در سطح سیستم‌عامل تضمین کامل ایجاد نمی‌کند؛ برای اجرای کد غیرقابل‌اعتماد باید sandbox و کنترل دسترسی سیستم‌عامل مستقل طراحی شود.
2. append-only بودن Audit در سطح برنامه، فایل را در برابر دستکاری مدیر سیستم یا بدافزار مصون نمی‌کند.
3. restore فعلاً پیش از جایگزینی مقصد، نسخه قبلی مقصد را به‌صورت خودکار snapshot نمی‌کند؛ قابلیت rollback باید در گردش‌کار بازیابی افزوده و آزموده شود.
4. حفظ اتمی بودن rename و رفتار مجوزها باید روی Windows 7 بررسی شود.
5. آزمون symlink در بعضی نسخه‌ها/تنظیمات Windows ممکن است به مجوز ویژه نیاز داشته باشد.
6. هیچ ادعایی درباره سازگاری runtime مدل، سرعت Qwen، مصرف RAM یا اجرای امن کد تا انجام آزمون روی دستگاه هدف مطرح نمی‌شود.

## وضعیت
این ممیزی و اصلاحات فقط در شاخه توسعه ثبت شده‌اند. شاخه `main` تغییر نکرده و هیچ merge یا انتشار نهایی انجام نشده است.


## یافته جدید از GitHub Actions و اصلاح
در اجرای CI شماره ۷ روی commit قبلی، هر دو job ویندوزی (Python 3.8 و 3.11) در سه آزمون snapshot/restore با خطای `OSError: [Errno 9] Bad file descriptor` شکست خوردند. علت این بود که فایل موقت پس از کپی با حالت فقط‌خواندنی دوباره باز و سپس به `os.fsync` داده می‌شد؛ این الگو روی runner ویندوز قابل اتکا نبود.

اصلاح در commit `e840d92cb2b1c12f24149b46c156b4d082bfe5c0` ثبت شد: کپی در descriptor نوشتنی انجام می‌شود، سپس flush و fsync پیش از بسته‌شدن descriptor اجرا می‌گردد. همچنین نسخه rollback قبل از جایگزینی مقصد موجود اضافه شد. آزمون متناظر در commit `59adba9bc2a58b06339efe84b6f050e6d2cc2c8d` اضافه شد.

نتیجه CI برای commit اصلاح‌شده باید پس از پایان اجرای جدید بررسی شود؛ تا آن زمان این اصلاح «ثبت‌شده، ولی هنوز CI-تأییدنشده» محسوب می‌شود.


## نتیجه نهایی CI پس از اصلاح (۶ نوامبر ۲۰۲۶)
اجرای workflow برای commit `59adba9bc2a58b06339efe84b6f050e6d2cc2c8d` با شناسه `42229303155` کامل و موفق شد. هر چهار job ماتریس زیر نتیجه `success` داشتند:
- Ubuntu / Python 3.8
- Windows latest / Python 3.8
- Windows latest / Python 3.11
- Ubuntu / Python 3.11

این نتیجه، اجرای موفق آزمون‌های واحد در runnerهای ابری ویندوز و لینوکس را تأیید می‌کند؛ اما معادل آزمایش روی Windows 7 SP1 واقعی کاربر یا سخت‌افزار Pentium G2020 نیست. همچنین CI فقط آزمون‌های موجود را اجرا می‌کند و جای آزمون قطع برق، خرابی دیسک، رقابت هم‌زمان فایل‌ها یا بازیابی crash-level را نمی‌گیرد.
