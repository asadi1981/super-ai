# سند معماری هسته مرکزی SUPER AI
نسخه: 1.0 — تاریخ: 2026-11-06
وضعیت: پیش‌نویس فنی قابل ممیزی؛ هنوز مبنای ساخت نسخه نهایی نیست.

## 1. هدف و اصول الزام‌آور
SUPER AI از یک هسته مشترک و دو محصول مستقل تشکیل می‌شود:
- SUPER AI Assistant: دستیار عمومی، مدیریت دانش و فایل‌ها.
- SUPER AI Programmer: محیط تخصصی توسعه نرم‌افزار، اجرای آزمون و رفع اشکال.
هسته مشترک با نام SUPER AI CORE مسئول هماهنگی مدل، حافظه، ابزارها، پروژه‌ها، امنیت و ثبت رویدادهاست. رابط کاربری و لایه اتصال سیستم‌عامل در هر محصول/سکو مستقل می‌ماند.

اصول:
1. کارکرد پایه بدون اینترنت؛ سرویس آنلاین فقط افزونه اختیاری.
2. استقلال هسته از مدل زبانی؛ مدل‌ها از طریق قرارداد یکسان قابل تعویض‌اند.
3. فارسی و راست‌چین در رابط و ورودی/خروجی.
4. هیچ عملیات مخرب یا انتشار/ارسال داده بدون مجوز روشن کاربر.
5. فایل اصلی بدون نسخه پشتیبان و تأیید جایگزین یا حذف نمی‌شود.
6. قابلیت‌ها بر اساس آزمون واقعی اعلام می‌شوند؛ «کنترل همه برنامه‌ها» تضمین نمی‌شود و از طریق افزونه‌های مجاز و رابط‌های قابل اتکا توسعه می‌یابد.

## 2. نمای معماری
لایه‌ها:
- UI مستقل: دسکتاپ Windows و برنامه Android.
- Application/API: فرمان‌ها، نشست‌ها، گردش‌کارها و مجوزها.
- Agent Runtime: تحلیل درخواست، شکستن کار به مراحل، انتخاب ابزار، کنترل نتیجه و توقف امن.
- Model Gateway: قرارداد یکنواخت برای مدل محلی و درگاه آنلاین اختیاری.
- Tool Runtime: ابزارهای فایل، ترمینال محدود، مفسرها، ساخت، آزمون و اتصال برنامه‌ها.
- Project & Knowledge Store: پروژه‌ها، حافظه، شاخص جست‌وجو و نسخه‌ها.
- Security/Audit: سیاست دسترسی، محیط اجرا، ثبت تغییرات و بازیابی.
- Platform Adapters: سازگارکننده‌های اختصاصی Windows و Android.

## 3. قراردادهای اصلی هسته
### 3.1 Model Provider
هر ارائه‌دهنده باید عملیات زیر را پیاده‌سازی کند:
- generate(messages, options) -> response
- health() -> status
- capabilities() -> فهرست قابلیت‌های واقعاً پشتیبانی‌شده
- cancel(request_id)
خروجی باید شامل متن، شناسه مدل، زمان اجرا، وضعیت پایان و خطا باشد. مدل نباید مستقیماً مجاز به اجرای ابزار یا تغییر فایل باشد؛ تصمیم ابزار فقط در Agent Runtime و تحت سیاست امنیتی انجام می‌شود.

### 3.2 Tool
هر ابزار دارای شناسه، شرح، ورودی/خروجی ساخت‌یافته، سطح خطر، نیازمندی مجوز، timeout و امکان لغو است. ابزارها به دسته‌های read-only، reversible-write و destructive/external تقسیم می‌شوند. دسته سوم نیازمند تأیید صریح و موردی است.

### 3.3 Project
هر پروژه دارای شناسه پایدار، نام، مسیر ریشه، زبان‌ها، تنظیمات ساخت، وابستگی‌ها، نسخه مبنا و وضعیت آزمون است. عملیات ابزار باید در محدوده ریشه پروژه انجام شود مگر مجوز جداگانه صادر شود.

## 4. اجزای اجرایی
1. Command Interpreter: تبدیل دستور فارسی به قصد، موجودیت‌ها، محدودیت‌ها و معیار اتمام.
2. Planner: تولید برنامه مرحله‌ای با پیش‌نیاز، ریسک، ابزار لازم و معیار موفقیت.
3. Executor: اجرای گام‌ها با timeout، لغو و ثبت نتیجه.
4. Verifier: بررسی خروجی با آزمون، مقایسه فایل، lint یا کنترل ساختاری.
5. Recovery Manager: بازگردانی تغییرات از snapshot/نسخه کنترل‌شده.
6. Memory Service: حافظه کوتاه‌مدت نشست، حافظه پروژه و دانش قابل جست‌وجو؛ داده حساس به‌صورت پیش‌فرض وارد حافظه بلندمدت نمی‌شود.
7. File Service: خواندن/نوشتن امن، تشخیص encoding، محدودیت اندازه و جلوگیری از path traversal.
8. Build & Test Service: فراخوانی ابزارهای نصب‌شده با مسیر و نسخه مشخص؛ نبود ابزار باید به‌عنوان مانع گزارش شود.
9. Connector Host: افزونه‌های برنامه‌ای با مجوز حداقلی و API رسمی؛ کنترل رابط گرافیکی فقط آخرین راهکار و با محدودیت است.

## 5. چرخه اجرای درخواست
1. دریافت درخواست و تشخیص زبان/هدف.
2. استخراج ابهام‌های حیاتی؛ فقط اگر بدون پاسخ امکان ادامه امن نیست سؤال شود.
3. تعیین محدوده فایل‌ها، ابزارها، دسترسی‌ها و معیار پذیرش.
4. ارائه برنامه کوتاه؛ برای کارهای کم‌خطر می‌تواند خودکار ادامه یابد.
5. ساخت snapshot از فایل‌های در معرض تغییر.
6. اجرای گام‌ها در sandbox یا پوشه کاری جداگانه.
7. اجرای آزمون‌ها و اعتبارسنجی مستقل از متن مدل.
8. گزارش تغییرات، خطاهای باقی‌مانده و راه بازگشت.
9. درخواست تأیید پیش از جایگزینی نهایی، حذف، نصب، ارسال شبکه‌ای یا انتشار.

## 6. امنیت و پایداری
- پیش‌فرض deny؛ ابزار فقط دسترسی اعلام‌شده را می‌گیرد.
- اجرای کد ناشناس در پوشه موقت، با timeout و محدودیت مسیر/حجم؛ در صورت نبود sandbox سیستم‌عامل، حالت محدود و هشداردهی فعال می‌شود.
- کلیدها و رمزها در فایل پروژه، Git یا log ذخیره نمی‌شوند.
- ثبت رویداد append-only شامل زمان، عامل، ابزار، مسیر، نتیجه و مجوز؛ حذف/ویرایش log از UI عادی ممنوع.
- snapshot پیش از تغییرات؛ نسخه‌بندی مبتنی بر diff یا کپی امن.
- پشتیبان‌گیری محلی و قابلیت خروجی رمزگذاری‌شده در مرحله بعد.
- دسترسی شبکه به‌طور پیش‌فرض خاموش؛ هر connector آنلاین مجوز و مقصد مشخص می‌خواهد.

## 7. انتخاب فناوری و سازگاری سکو
### Windows 7 SP1 x64، Pentium G2020، RAM 4GB
- رابط نسخه نخست: Python 3.8 + Tkinter برای بیشترین سازگاری با محیط موجود.
- هسته نسخه نخست: ماژول‌های Python 3.8 خالص تا حد امکان؛ جداسازی لایه‌های سیستم‌عامل.
- اجرای مدل: runtime بومی مبتنی بر llama.cpp/GGUF باید با کامپایل هدف‌گذاری‌شده برای Windows 7 و دستورالعمل CPU آزمایش شود. هیچ binary جدیدی بدون تست روی همین دستگاه تأییدشده تلقی نمی‌شود.
- مدل شروع آزمایش: qwen2.5-0.5b-instruct-q4_k_m.gguf؛ کیفیت برنامه‌نویسی حرفه‌ای آن قطعی نیست و باید با مجموعه آزمون فارسی/کدنویسی سنجیده شود.
- محدودیت RAM: بارگذاری مدل کوچک، context محدود، عدم اجرای هم‌زمان مدل و چند ابزار سنگین، و امکان حالت rule/tool-first برای وظایف فایل و ساخت.
- Ollama یا نسخه‌های جدید ابزارها نباید پیش‌فرض فرض شوند؛ سازگاری Windows 7 جداگانه بررسی می‌شود.

### Android 11
- محصول مستقل Android با Kotlin و رابط بومی.
- Model Runtime از طریق کتابخانه بومی/NDK و رابط JNI؛ بسته مدل جداگانه و قابل انتقال.
- مجوز فایل‌ها، اجرای پس‌زمینه، مصرف باتری و فضای ذخیره‌سازی مطابق Android.
- ارتباط بین موبایل و دسکتاپ در نسخه نخست ضروری نیست؛ انتقال پروژه از طریق فایل/بسته کنترل‌شده انجام می‌شود.
- قابلیت‌های سیستم‌عامل از طریق Android Adapter ارائه می‌شوند، نه کد مشترک UI.

## 8. مدل داده محلی المقترح
- config/: تنظیمات غیرمحرمانه و پروفایل‌ها
- models/: مدل‌ها و metadata/checksum
- projects/: پروژه‌های کاربر
- workspace/: نسخه کاری موقت و sandbox
- memory/: حافظه ساختاریافته و شاخص جست‌وجو
- backups/: snapshotها و پشتیبان‌ها
- logs/: گزارش رویداد و خطا
- plugins/: افزونه‌های تأییدشده
مسیرها در Windows نسبی به پوشه نصب/حمل‌پذیر و در Android داخل فضای خصوصی برنامه تعریف می‌شوند. داده‌ها با شناسه نسخه schema مهاجرت می‌کنند؛ هیچ مهاجرتی بدون backup اجرا نمی‌شود.

## 9. دامنه نسخه اول (MVP)
داخل دامنه:
- دستیار فارسی آفلاین با مدل محلی کوچک.
- مدیریت نشست و حافظه پروژه ساده.
- خواندن/نوشتن امن TXT, MD, JSON, CSV, Python.
- ساخت و اجرای پروژه Python در workspace محدود، با گزارش خروجی و خطا.
- ابزارهای پایه بررسی فایل، جست‌وجو، diff و backup.
- دو رابط مستقل؛ در شروع تمرکز پیاده‌سازی دسکتاپ روی Windows 7 و نمونه فنی Android برای اعتبارسنجی runtime.
خارج از دامنه نسخه اول:
- تضمین برنامه‌نویسی خودکار در سطح توسعه‌دهنده ارشد.
- کنترل عمومی هر نرم‌افزار ثالث بدون API/افزونه اختصاصی.
- انتشار خودکار در فروشگاه‌ها، دسترسی ریشه، تغییر فایل‌های سیستمی.
- همکاری ابری/همگام‌سازی خودکار و استفاده آنلاین اجباری.

## 10. معیارهای پذیرش فنی
- راه‌اندازی و گفت‌وگوی پایه بدون شبکه.
- تشخیص و گزارش روشن نبودن/خرابی مدل.
- عدم دسترسی ابزار به بیرون از workspace بدون مجوز.
- ساخت یک برنامه Python نمونه، اجرای تست و گزارش نتیجه قابل تکرار.
- بازگردانی دقیق فایل پس از rollback.
- حفظ داده پس از بستن و اجرای مجدد برنامه.
- نمایش فارسی/RTL صحیح.
- اجرای دسکتاپ روی Windows 7 واقعی با RAM 4GB؛ ثبت زمان پاسخ و مصرف حافظه.
- Android 11: نصب مستقل، بارگذاری مدل آزمایشی و یک prompt آفلاین موفق روی دستگاه واقعی.

## 11. ریسک‌های باز و روش بستن
| ریسک | اثر | اقدام لازم |
|---|---|---|
| کیفیت مدل 0.5B | پاسخ‌های ضعیف و کد نادرست | مجموعه آزمون و مقایسه مدل‌های کوچک |
| محدودیت RAM چهار گیگ | کندی/عدم بارگذاری | اندازه‌گیری مصرف و context کوتاه |
| Windows 7 قدیمی | ناسازگاری binary/dependency | ساخت و آزمون روی دستگاه هدف |
| امنیت اجرای کد | آسیب فایل/سیستم | workspace، allowlist، timeout و تأیید |
| Android runtime | تفاوت ABI/حافظه | نمونه JNI و آزمون روی Android 11 |
| کنترل برنامه‌های ثالث | APIهای متفاوت | معماری افزونه به‌جای ادعای سازگاری عمومی |

## 12. تصمیم‌های نیازمند آزمون، نه سؤال از کاربر
این موارد با آزمایش فنی تعیین می‌شوند: runtime قابل اجرا روی Windows 7، سرعت و کیفیت مدل Qwen 0.5B، مدل جایگزین سبک، حجم بسته نهایی، و امکان اجرای inference آفلاین روی گوشی Android 11. تا پیش از آزمون، هیچ‌کدام «تأییدشده» اعلام نمی‌شوند.
